# Windows QQ 消息转发器：未来版本优化改进方向

> 本文档用于记录下一阶段及后续版本的规划。后续开始新版本开发时，应先阅读本文档，再根据当前代码状态、Windows QQ 客户端版本和实际资源情况制定详细方案。

## 1. 规划背景

当前项目已经支持以下能力：

- 通过 Windows `UserNotificationListener` API 监听 QQ 通知；
- 在通知 API 不可用时回退到 UI Automation 和快速轮询；
- 监听多个 QQ 群或联系人；
- 将消息转发到一个 B 群 QQ 官方机器人；
- 失败消息重试和 QQ 聊天窗口历史补发；
- Web UI 管理监听会话、运行模式、检查结果和补发操作；
- 运行前检查、主动消息测试以及本地 SQLite 消息队列。

下一阶段希望支持多个机器人、多个独立实例，以及系统资源评估和保护。

## 2. 目标功能

### 2.1 单个实例使用多个机器人转发

一个实例可以监听一组 QQ 会话，并将同一批消息转发给多个机器人。每个机器人拥有自己的目标群组。

示例：

```text
实例1：监听 QQ 群 A、联系人甲 → 机器人1 → B 群1
实例2：监听 QQ 群 B、联系人乙 → 机器人1、机器人2 → B 群2、B 群3
实例3：监听联系人丙       → 机器人3、机器人4 → B 群4、B 群5
```

### 2.2 创建和管理多个实例

一个统一的 Web 控制面管理多个监听转发实例。每个实例拥有独立的配置、数据库、日志、运行状态和子进程。

实例应支持：

- 创建；
- 编辑；
- 删除；
- 启动；
- 停止；
- 重启；
- 查看实例状态；
- 查看实例日志；
- 查看实例消息队列。

### 2.3 实例资源评估

在启动新实例前，检测当前 Windows 主机资源，并给出可创建实例数量的建议值。

页面应显示：

- 当前运行实例数；
- 建议最多运行实例数；
- 预计还可以启动的实例数；
- 当前 CPU 使用率；
- 当前可用内存；
- 磁盘剩余空间；
- 当前每个实例的 CPU 和内存占用；
- 主要限制因素和风险提示。

该数量是保守估算值，不应承诺绝对保证。图片处理、历史补读、通知高峰和 QQ UI Automation 操作可能造成瞬时资源增加。

## 3. 可行性评估

| 功能 | 可行性 | 改造规模 | 结论 |
| --- | --- | --- | --- |
| 一个实例配置多个机器人 | 高 | 中等 | 推荐优先实施 |
| 多个实例独立运行 | 中高 | 较大 | 可以实施，但需要统一实例管理器 |
| 资源检测和实例数量估算 | 高 | 中等 | 推荐作为多实例功能的一部分实施 |
| 多实例共享 QQ 通知采集 | 高 | 较大 | 推荐后续优化，减少重复扫描 |
| 多实例同时操作 QQ 窗口 | 有条件可行 | 中等 | 必须增加跨进程 UI 锁或集中式 UI 工作进程 |

总体结论：方案可行，但不能只在当前配置文件中增加几个数组字段。消息投递模型、实例生命周期、资源占用和全局资源冲突都需要一起设计。

## 4. 当前架构与需要解决的问题

### 4.1 当前消息投递模型是单目标

当前结构大致为：

```text
监听会话 → 本地消息队列 → 一个 OfficialQqBotSender → 一个 group_openid
```

多机器人后应变为：

```text
监听会话 → 统一消息队列
                    ├── 机器人1 → 目标群1
                    ├── 机器人2 → 目标群2
                    └── 机器人3 → 目标群3
```

不能继续只用一条消息的 `sent` 状态表示整体成功，因为可能出现部分成功：

```text
机器人1发送成功
机器人2发送失败
机器人3发送成功
```

### 4.2 多机器人需要独立投递状态

建议保留消息主表，并增加消息投递明细表：

```text
messages
message_deliveries
```

`message_deliveries` 至少应包含：

```text
message_key
bot_id
status
attempts
last_error
sent_at
```

状态建议包括：

```text
pending
sending
sent
failed
discarded
```

重试时只处理失败的机器人，避免已成功的机器人收到重复消息。

图片暂存文件必须等所有目标机器人发送完成后再删除。如果只有部分机器人发送成功，图片文件必须继续保留。

### 4.3 当前配置只支持一个机器人

目前 `DestinationConfig` 只有一个：

- `app_id`；
- `client_secret_env`；
- `group_openid`；
- `message_prefix`。

后续应改为机器人配置列表，每个机器人至少包含：

```toml
[[destinations]]
bot_id = "bot-1"
app_id = "机器人 AppID"
client_secret_env = "QQ_BOT_1_CLIENT_SECRET"
group_openid = "目标群 group_openid"
message_prefix = "[转发]"
```

机器人唯一身份应使用 `app_id` 或明确的 `bot_id + app_id`，不能只使用环境变量名判断。环境变量名只是密钥的读取方式，不一定能代表机器人身份。

### 4.4 当前网关连接只支持一个机器人

当前使用单个 `run_gateway_forever(destination, stop_event)`。多机器人后需要为每个机器人独立维护：

- API 客户端；
- Token；
- WebSocket；
- 会话序号；
- 重连状态；
- 失败状态；
- 日志上下文。

建议增加类似以下的统一调度入口：

```python
run_gateways_forever(destinations, stop_event)
```

日志必须包含 `instance_id` 和 `bot_id`，否则多个实例或机器人同时异常时难以定位。

### 4.5 当前单实例锁不是全局资源锁

当前 `forwarder.lock` 位于实例数据库目录中，只能防止同一个数据目录被重复启动。多个配置目录可以绕过这把锁，因此需要增加全局资源登记和全局锁。

建议增加：

```text
control.sqlite3
resource_registry
```

或者使用带跨进程锁保护的实例登记文件。

登记内容至少包括：

```text
resource_type = listener / bot
resource_key
instance_id
status
claimed_at
```

登记和校验必须在同一个全局锁或 SQLite 事务中完成，避免两个实例同时检查时都认为资源可用。

### 4.6 QQ UI 操作锁必须跨进程

当前 `QQ_UI_LOCK` 是 Python 进程内线程锁。多个实例作为多个进程运行后，进程之间无法互相感知这把锁。

多个实例可能同时：

- 切换 QQ 会话；
- 读取聊天记录；
- 复制图片；
- 恢复前台窗口。

这可能导致读错会话、复制错图片和窗口焦点互相抢占。

正式支持多实例前，必须选择以下方案之一：

1. 使用共享文件锁，例如 `data/qq-ui.lock`；
2. 使用 Windows 命名互斥体；
3. 建立单独的 QQ UI 工作进程，所有实例通过队列请求 UI 操作。

第一阶段推荐使用跨进程文件锁，改造成本较低；如果图片和历史补读并发量较高，再考虑集中式 UI 工作进程。

### 4.7 Windows 通知可能被重复扫描

当前每个实例都会创建自己的 `WindowsNotificationReader`。实例数量增加后，可能出现：

- 多次扫描同一批 Windows 通知；
- 重复注册通知事件；
- 多个实例在回退 UI Automation 时重复扫描通知弹窗；
- CPU 消耗随实例数增加。

第一阶段可以让每个实例只过滤自己配置的会话，但正式扩展时建议采用：

```text
全局通知采集器
    ↓
按照 listener_name 路由到实例队列
```

这样 Windows 通知只读取一次，实例只负责处理自己的消息和目标机器人。

## 5. 资源检测设计

### 5.1 检测范围

系统级指标：

- CPU 核心数；
- 当前 CPU 使用率；
- 总内存和可用内存；
- 磁盘剩余空间；
- Python 进程数量；
- 当前运行实例数量。

实例级指标：

- 实例 PID；
- 实例 CPU 使用率；
- 实例内存占用；
- 监听会话数量；
- 机器人数量；
- 待发送消息数；
- 失败消息数；
- 最近一段时间的消息处理量。

### 5.2 估算模型

建议使用保守模型计算建议上限：

```text
实例预计资源 = 基础监听资源
             + 机器人数量 × 单机器人资源
             + 图片处理资源
             + 历史补读资源
```

然后分别计算：

```text
内存上限 = 可用于本项目的内存 × 安全系数 ÷ 单实例预计内存
CPU 上限 = 可用于本项目的 CPU 容量 ÷ 单实例预计 CPU
建议上限 = min(内存上限, CPU 上限, 配置的硬上限)
```

安全系数建议从 0.6～0.7 开始，后续根据真实运行数据调整。

### 5.3 估算值和实测值

初始版本可以使用配置估算。运行过至少一个实例后，使用最近一段时间的实际 CPU 和内存数据校准：

- 空闲监听状态；
- 普通文本消息状态；
- 历史补读状态；
- 图片处理状态；
- 多机器人发送状态。

页面要明确区分：

```text
估算建议上限
实测当前占用
资源风险提示
```

不能因为当前空闲就认为高峰期一定可以运行同样数量的实例。

## 6. 实例配置建议

建议从单配置文件迁移为一个实例清单和多个实例配置：

```text
instances/
  default/
    config.toml
    data/forwarder.sqlite3
    data/forwarder.log
  instance-2/
    config.toml
    data/forwarder.sqlite3
    data/forwarder.log
```

统一管理文件可以记录：

```text
instance_id
display_name
config_path
status
pid
created_at
updated_at
```

现有单实例 `config.toml` 应作为默认实例平滑迁移，迁移前必须保留原数据库和日志，避免历史队列丢失。

## 7. 冲突校验规则

### 7.1 机器人唯一性

同一个 `app_id` 只能归属于一个实例。

示例：

```text
实例1使用机器人1
实例2再次使用机器人1 → 拒绝启动
```

提示信息应包含：

- 冲突机器人；
- 已归属实例；
- 当前尝试启动的实例；
- 解决建议。

### 7.2 监听会话唯一性

同一个群名或联系人名称只能归属于一个实例。

名称比较应统一经过标准化：

- 去除首尾空格；
- 连续空白归一化；
- 大小写不敏感比较；
- 展示时保留用户原始名称。

注意：仅使用名称无法解决 QQ 中同名联系人或同名群的问题。后续如果 QQ UI 能获取稳定会话 ID，应优先使用会话 ID，名称只作为展示和辅助匹配字段。

### 7.3 启动时原子校验

以下操作都需要在全局锁保护下完成：

1. 读取实例配置；
2. 检查机器人和监听会话是否冲突；
3. 检查系统资源；
4. 登记资源归属；
5. 启动实例进程。

如果进程启动失败，必须回滚资源登记，不能留下“已占用但实际未运行”的脏数据。

## 8. Web UI 规划

建议把当前单实例页面升级为以下结构：

### 实例总览

- 实例卡片列表；
- 每个实例的运行状态；
- PID；
- 监听会话数量；
- 机器人数量；
- 待发送和失败消息数；
- 启动、停止、重启按钮。

### 实例编辑

- 实例名称；
- 监听群或联系人列表；
- 机器人列表；
- 每个机器人对应目标群；
- 密钥环境变量名；
- Dry-run 开关；
- 日志和数据库位置。

### 全局检查

- 资源冲突检查；
- 机器人重复使用检查；
- 监听会话重复使用检查；
- 系统资源检查；
- QQ 客户端和通知权限检查；
- 每个实例的运行前检查。

### 操作反馈

所有长耗时操作都需要：

- loading 状态；
- 防重复点击；
- 明确的成功/失败反馈；
- 失败时显示可执行的处理建议；
- 多机器人操作时显示每个机器人结果。

## 9. 分阶段实施计划

### 阶段一：单实例多机器人

目标：不引入多实例，先验证多目标投递模型。

实施内容：

- DestinationConfig 改为机器人列表；
- 增加 `bot_id`；
- 增加消息投递明细表；
- 每个机器人独立 API 和网关；
- 支持部分成功、部分失败；
- 只重试失败机器人；
- 图片文件在全部目标完成后清理；
- Web UI 增加机器人管理；
- 主动测试支持单机器人和全部机器人。

验收标准：

- 一条消息能够发送到两个以上目标群；
- 一个机器人失败不会影响其他机器人；
- 重试不会重复发送已成功目标；
- 重启后投递状态可以恢复；
- 旧单机器人配置能够迁移。

### 阶段二：多实例基础管理

目标：能够创建和运行多个互不冲突的实例。

实施内容：

- 实例清单；
- 实例配置目录；
- 实例子进程管理；
- 实例级数据库和日志；
- 全局资源登记；
- 机器人冲突校验；
- 监听会话冲突校验；
- 实例级状态和日志页面。

验收标准：

- 不同监听会话和机器人可以同时运行；
- 重复机器人无法启动；
- 重复监听会话无法启动；
- 停止实例后资源可以重新分配；
- 子进程异常退出后状态可以恢复；
- Web 控制面不会重复启动实例。

### 阶段三：跨进程 QQ UI 协调

目标：保证多个实例同时运行时不会互相干扰 QQ 窗口。

实施内容：

- 跨进程 QQ UI 锁；
- 历史补读互斥；
- 图片复制互斥；
- UI 操作超时和取消；
- 前台窗口状态恢复；
- UI 操作日志加入实例和会话信息。

验收标准：

- 两个实例同时收到图片消息时不会复制错图片；
- 两个实例同时进行历史补读时不会读错会话；
- 一个实例 UI 操作卡住不会永久阻塞其他实例；
- QQ 窗口焦点可以尽量恢复。

### 阶段四：中央通知采集和资源保护

目标：减少重复扫描并提高多实例稳定性。

实施内容：

- 一个全局通知采集器；
- 按监听会话路由消息；
- 系统资源监控；
- 实例资源监控；
- 建议实例上限；
- 启动前容量检查；
- 超过阈值时阻止新实例启动；
- 运行中高资源告警。

## 10. 风险与限制

- 个人 QQ 没有公开稳定的第三方群消息 API，扩展实例数量不会改变通知监听的根本限制；
- Windows 通知可能被合并、覆盖或延迟；
- UserNotificationListener 事件在不同 Windows 环境中可能不可用；
- UI Automation 对 QQ 版本和界面布局敏感；
- 同名群或联系人无法仅通过名称准确区分；
- 多机器人 API 可能有频率限制、并发限制或权限限制；
- 多实例同时操作 QQ 窗口会增加前台焦点和图片复制失败概率；
- 资源估算无法覆盖所有消息高峰和图片突发场景；
- 机器人密钥仍只能通过环境变量或安全存储读取，不能写入 Git 或普通日志。

## 11. 下一版本开发前检查清单

开始实施前必须确认：

- [ ] 明确单实例多机器人还是直接进入多实例开发；
- [ ] 确认机器人唯一身份字段使用 `app_id` 还是 `bot_id + app_id`；
- [ ] 确认每个机器人是否只对应一个目标群；
- [ ] 设计消息投递明细表和迁移方案；
- [ ] 设计现有 `config.toml` 和 SQLite 数据迁移方案；
- [ ] 设计全局实例清单和资源登记；
- [ ] 设计跨进程资源锁；
- [ ] 决定 QQ UI 使用共享文件锁还是集中式 UI 工作进程；
- [ ] 确认是否先保留每实例独立通知采集；
- [ ] 确定资源估算的安全系数和硬上限；
- [ ] 补充冲突校验、部分成功、进程异常和资源不足测试；
- [ ] 在 Windows 实机验证多个机器人和多个实例的 CPU、内存、UI 操作影响；
- [ ] 为每个阶段定义可回滚方案。

## 12. 推荐结论

推荐按照以下顺序推进：

```text
单实例多机器人
        ↓
多实例管理和资源冲突校验
        ↓
跨进程 QQ UI 锁
        ↓
中央通知采集和资源监控
```

不要在第一步同时引入多机器人、多实例、中央采集和资源自动限制。应先验证单实例多机器人投递状态，否则出现问题时难以判断是消息采集、实例管理还是机器人投递造成的。
